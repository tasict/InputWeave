# The Linux packages

`build-deb.sh amd64|arm64` builds `dist/inputweave_<version>_<arch>.deb` in the Linux containers (`scripts/linux-container/README.md`): amd64 in `inputweave-linux`, arm64 in `inputweave-linux-arm64`. `scripts/linux-container.sh deb` builds both. They are built on Ubuntu 24.04, the oldest release they are for, and install there and on later Ubuntu releases and Debian 13. Their library dependencies are what `dpkg-shlibdeps` reads from the libraries' symbols files: GTK 4.12 or later (the app is built against GTK 4.14 with gtk4-rs' `gnome_46` feature, but calls nothing that came after 4.12) and libadwaita 1.5 or later, which is what keeps it off anything older than Ubuntu 24.04.

## How it fits together

- **The agent's unit is named for the portals.** xdg-desktop-portal tells a host app (one not in Flatpak) by the systemd unit it runs in: `app-<app id>@<instance>.service`. The template `app-cc.ctsite.inputweave@.service` has `DefaultInstance=agent`, so it runs as `app-cc.ctsite.inputweave@agent.service`, and the desktop's remote desktop and input capture dialogs name the app `cc.ctsite.inputweave` ("InputWeave", from its desktop entry) and remember what was allowed under it.
- **It starts with the desktop session.** The unit is `WantedBy=graphical-session.target` and `PartOf=` it, so it starts at each login with that session's environment and stops at logout. GNOME and KDE Plasma start `graphical-session.target` and import the session's `WAYLAND_DISPLAY`/`DISPLAY` into the user manager. Cinnamon, Xfce and MATE do neither, and nothing stops the agent when their sessions end; for them the autostart entry runs `start-agent` at each login, which imports the session's display variables into the user manager, removes the ones the session does not have (an X11 login after a Wayland one must not keep `WAYLAND_DISPLAY`), and restarts the agent, which starts it if it is not running. The entry carries `X-GNOME-HiddenUnderSystemd=true` and `X-systemd-skip=true`, so GNOME and systemd's autostart generator (KDE) skip it, and `TryExec`, so after `apt remove` (it is a conffile, kept until purged) it does nothing.
- **The package enables the unit for every user** with `deb-systemd-helper --user` (init-system-helpers 1.66 handles the template and `DefaultInstance`), as `dh_installsystemduser` would: a new installation enables it, an upgrade keeps an administrator's choice, removing masks it and purging takes the symlinks and the mask away. No maintainer script starts anything; a user's service is theirs to start, so it starts at the next login (or `systemctl --user start app-cc.ctsite.inputweave@agent.service`).
- **The app does not open at login by default**, as on macOS and Windows: the agent does the work, and opens the app when the user has to decide something. The app's own "Open at login" writes `~/.config/autostart/cc.ctsite.inputweave.desktop`.
- **D-Bus starts the app in a unit of its own.** The desktop entry is `DBusActivatable`, so launchers activate the app over D-Bus too. The D-Bus service names `SystemdService=app-cc.ctsite.inputweave.service` (`Type=dbus`, `BusName=cc.ctsite.inputweave`, running `inputweave-app --gapplication-service`), so the app runs in a cgroup the portals read as `cc.ctsite.inputweave`, like the agent, and its log is under its unit. Where the session bus is not started by systemd, D-Bus runs the `Exec` line itself. Started from a terminal, the app runs outside the unit, and a second launch hands over to the running one as GApplication does.
- **The firewall is the user's.** The package applies no rule. Where ufw is on (it is off on a new Ubuntu), other devices reach the agent only once `sudo ufw allow InputWeave` lets the profile's ports in (QUIC on UDP 47820, mDNS on UDP 5353); firewalld's service is `inputweave`: once the package is installed, `sudo firewall-cmd --reload` (so firewalld reads the new service), then `sudo firewall-cmd --add-service=inputweave --permanent` and `sudo firewall-cmd --reload` again. The agent reads `/etc/ufw/ufw.conf` and, where it may, the rules, and the app says when ufw is on and does not let the agent's port or mDNS in (`Status.firewall`, with the ports kept out). A port changed in the configuration needs its own rule.
- **Logs go to the journal**: `journalctl --user -u app-cc.ctsite.inputweave@agent.service` for the agent, `journalctl --user -u app-cc.ctsite.inputweave.service` for the app when D-Bus started it (`_COMM=inputweave-app` finds it however it was started).
- **Updates come from the package repository.** The package installs `/etc/apt/sources.list.d/inputweave.sources`, a deb822 source for a flat repository at `https://inputweave.ctsite.cc/latest/` (`Suites: ./`), so `apt upgrade` and the desktop's software updates install new versions. The website redirects that address to the latest release where the releases are hosted (GitHub Releases now; `docs/architecture.md` §12), so the host can change without a new package. Each release carries the repository's `InRelease`, `Release`, `Release.gpg`, `Packages` and `Packages.gz` beside the two packages (`scripts/release.sh` writes them); `latest` always leads to the newest release, so its index names its own packages. The signing key (`inputweave-archive-key.asc`, ed25519, fingerprint `DA65 B795 D2F3 984F 0B30 5013 C3AF 4DF7 6FC8 7E0E`) is embedded in the source's `Signed-By` field rather than installed as a keyring under `/usr/share/keyrings`: the source is a conffile and stays after `apt remove` until purged, and a keyring under `/usr` would leave with the package, after which apt would fail on a source whose key is gone. A line `Enabled: no` in the file turns the repository off, and upgrades keep that.
- **Recommends** xdg-desktop-portal 1.18 or later with the GNOME or KDE backend, which have the remote desktop and input capture portals. xdg-desktop-portal-wlr has neither; on wlroots compositors InputWeave uses their own protocols.

## Checking a package

- `scripts/linux-container.sh check-deb` installs `dist/inputweave_<version>_amd64.deb` into fresh `ubuntu:24.04` and `debian:trixie` containers (`check-install.sh`): the dependencies resolve, both programs run, the unit is enabled for every user, `appstreamcli` and `desktop-file-validate` accept the metainfo and desktop entries, `ufw app info InputWeave` reads the ufw profile (and no rule is added) and the firewalld service is there; `check-firewalld.sh` (also run by `check-deb`, in a throwaway container of the native image, since firewalld pulls systemd, whose postinst fails in a fresh image on older host kernels such as Linux 5.10) reads the service with `firewall-offline-cmd --info-service=inputweave`, and remove, reinstall and purge leave what they should (nothing, after purging).
- `sh packaging/linux/check-activation.sh dist/inputweave_<version>_amd64.deb`, in the native container, starts the app the way the agent will, from the package's D-Bus service file on a private session bus with Xvfb (that bus is not systemd's, so it runs the `Exec` line; `SystemdService=` takes over on a desktop): `ActivateAction("background")` brings it up with only its tray icon, `Activate` opens the window.
- For the unit itself, `systemd-analyze --user verify` needs `XDG_RUNTIME_DIR` and the binary at the `ExecStart` path; `--root` does not work with `--user`, so check a copy whose `ExecStart` points into the extracted package.
- The arm64 package's programs run under `qemu-aarch64 -L /usr/aarch64-linux-gnu` (the agent) and `qemu-aarch64 -L /` (the app, with the arm64 GTK of the arm64 container).
