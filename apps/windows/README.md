# InputWeave for Windows

The notification area app (WinUI 3, C#, .NET 9): the tray icon, its menu and panel, the InputWeave window with its five pages and the arrangement canvas, Add Device, the pairing code shown when another computer adds this one, first-run setup, the HUD, the cursor locator, system notifications and File Explorer's Send To. The MSI does not install the app yet.

- `InputWeave.sln`: the solution. Its platforms are x64 (the default) and ARM64.
- `InputWeave/`: the app, unpackaged and self-contained: the .NET runtime and the Windows App SDK runtime are in its folder, so nothing has to be installed first. It only talks to the background service over the agent's named pipe, `\\.\pipe\InputWeave\agent-<session id>`, and never links Rust.
  - `Program.cs`: one app per Windows session; opening it again hands its arguments to the one already running over a pipe only the same user can open, which then opens its panel (bringing back a hidden tray icon), or first-run setup if it started for something else (in the background, by Send To, for a notification) and setup has neither been finished nor shown yet, or sends the files from `--send`. What opens at launch for which arguments is decided in `InputWeave.Core` (`Support/Launch.cs`, `Support/LaunchArguments.cs`). `--send <paths>` is what the Send To shortcut runs; `----AppNotificationActivated:` is how Windows starts the app for a click on one of its notifications; `--background` is how the background service's broker starts it when the user has to see or answer something (a pairing code, a file offer): only the tray icon, never setup or the main window on its own, but the pairing code window and notifications as usual, and a running app that gets it does nothing; `--unregister` removes what the app registered for the current user (notifications, the Send To shortcut, opening at login, its settings) and quits, for the uninstaller. Arguments for testing and screenshots: `--show-panel` opens the panel at launch and keeps it open without focus; `--show-window [page]` opens the main window (`general`, the default, `devices`, `arrangement`, `files` or `troubleshooting`, also as `--show-window=devices`); `--show-add-device` opens Add Device over it; `--show-pairing-code` shows a sample pairing code instead of the service's; `--show-setup [step]` opens first-run setup at a step (`welcome`, `name`, `network`, `connect`, `entercode`, `arrange`, `tryit`); `--show-hud ["text"]` shows the HUD; `--show-locator [seconds]` shows the cursor locator (the cursor growing) at the cursor, held as it is that many seconds in for 20 seconds when given, still following the cursor; `--show-notification received|folder|offer|service` posts a sample notification; `--show-sample-transfers` shows sample folder rows (going, finished, finished with failures) in the panel and on the File Transfers page instead of the service's; `--show-sample-devices` numbers the computers for the jump shortcuts and gives the first other one a name of its own here, as a service that does both would report them; `--show-identify [seconds]` shows this computer's name on each of its screens, as when the screens are identified; `--simulate-drag-enter <paths>` has a drag of those files enter a drag strip and leave it four seconds later, as the strip's drop target would see it; `--simulate-drag-arrived <paths>` offers those files and folders as if dragged here from another computer two seconds after the app connects (press the mouse button first), and copies them into the staging folder once dropped instead of asking the service; `--show-hud key:<key>:<value>…` shows one of the app's strings in the HUD; `--language en-US` overrides Windows' display language. A window opened this way stays above the others, since an app started from a scheduled task does not get the foreground, and setup does not open by itself.
  - `Tray/`: the tray icon ([H.NotifyIcon](https://github.com/HavenDV/H.NotifyIcon)), the menu its right click and the panel's More button share (with Identify Screens), and the quit dialog.
  - `Panel/`: the panel the left click opens (borderless, always on top, Mica, anchored above the taskbar, closed when it loses focus), its exception rows and its transfer rows, which the File Transfers page uses too, where finished rows can also be removed from the history (their × or context menu, and Clear History… for all of them). Problems dismissed from the panel stay dismissed after the app restarts (`HKCU\Software\InputWeave\App`, `DismissedTransfers`), and those already in the history when the app first connects are not shown, as they are no news.
  - `Main/`: the main window (`NavigationView`, Mica, at least 760 × 520, hidden rather than closed) and its pages: Arrangement (with Identify Screens), Devices, File Transfers, General, Troubleshooting, and the device inspector the first two share, where another computer gets a name used only here, a cursor speed (a slider sent when let go of, or a moment after the keys move it; the service's value shows again once it answers, so a refused one goes back), and the clipboard and files can be turned off with it; an offline one that can be woken says since when it is offline and has Wake (disabled while it is being woken or the request has no answer yet), with a note when it didn't wake up or can't be woken yet. General's Switching has the switch that wakes a sleeping computer as the cursor is pushed toward it when the service can wake computers. General's Shortcuts (`ShortcutsSection.cs`, with the switch for pressing Ctrl twice to take back control when the service reports it) records a hotkey in a box that takes the focus and every key pressed in the window: the key by its scan code (`InputWeave.Core/Generated/KeyCodes.cs`, from `cargo xtask keymap`), the modifiers by their key state; no keyboard hook, so combinations the shell keeps (Win + L) never arrive. The pages are built in code from settings-style cards (`Ui.cs`).
  - `Canvas/`: the arrangement canvas, drawn with XAML shapes, with each computer's jump shortcut beside its name where there is room, and a moon after the name of one that can be woken (Wake in its context menu); the panel's mini map is its compact mode. Desktop pictures are decoded with `BitmapImage` once they pass `InputWeave.Core`'s checks.
  - `Pairing/`: the pairing flow (`PairingFlow`), which Add Device (a ContentDialog over the main window) and first-run setup both show, and the pairing code window (centered, on top, never activated).
  - `Setup/`: first-run setup (620 × 520, Mica), opened at launch until it is finished or put off (`HKCU\Software\InputWeave\App`, `FinishedSetup`), and from the menu's Run Setup Again….
  - `Drag/`: dragging files to and from other computers, on OLE threads of their own (`OleThread`: single-threaded apartment, OLE initialized, its own message loop) so WinUI never waits on a drag. `SeamStrips`: invisible strips (layered at 1/255 opacity, topmost, never activated) along the edges the cursor can leave by, registered as drop targets; they let the pointer through (`WS_EX_TRANSPARENT`) except while a mouse button is down that went down outside them (a press on a strip, as on the taskbar below one, keeps them clear until the button is up), since `HTTRANSPARENT` only passes hit tests to windows of the same thread. A drag of files entering one sends `BeginDrag`; the drop on a strip copies nothing (`DROPEFFECT_COPY`, never move); leaving the strips without crossing sends `EndDrag` for the drag id the answer to `BeginDrag` gave, whether or not the status naming it has come yet. The strips are placed again only when the arrangement, the computers a drag can go to (connected, files not turned off) or sharing, the lock and being controlled change. `PromisedDrag` and `FilePromise`: the drag another computer offers, started under the cursor after pressing the held button again on an invisible window of the drag's thread (`DragPad`; OLE's loop only hears the mouse when the press landed on its thread), with a data object of `CFSTR_FILEDESCRIPTORW` and `CFSTR_FILECONTENTS` and `IDataObjectAsyncCapability`, received through a staging folder under `%LOCALAPPDATA%\InputWeave\drag`. COM objects are source-generated (`[GeneratedComInterface]`, `[GeneratedComClass]`, `Ole.cs`), so publishing can trim.
  - `Overlay/`: the HUD, the cursor locator and the names shown when the screens are identified (one window per monitor, a pixel short of its bottom so Windows does not take it for an app in full screen): borderless windows above all others that never take the focus, let clicks through, and are clear wherever they draw nothing (a clear `SystemBackdrop`, the window background erased to nothing, and DWM composing with alpha). The cursor locator grows a copy of the cursor shown now, never the system cursor itself: `CursorPicture` reads it (`GetCursorInfo`, the standard arrow when none is shown) and copies it at the peak size, as sharp as Windows gives it: a system cursor loaded at that size from the file the user's cursor scheme names (`HKCU\Control Panel\Cursors`; reloading one with `LR_COPYFROMRESOURCE` only stretches USER32's built-in drawing), else reloaded with `CopyImage` (`LR_COPYFROMRESOURCE`), else stretched, else as it is, reading the copy through `GetIconInfo` and `GetDIBits`; `LocatorWindow` shows it in a window the size of the copy at its peak that moves to the cursor every frame (`CompositionTarget.Rendering`, `GetCursorPos`), the copy shrinking inside it towards its hotspot through a render transform, and reads the cursor again when its shape changes on the way.
  - `Support/`: the strings, the brand colors, the Windows service's state, the app's preferences (`HKCU\Software\InputWeave\App`) and opening at login (`HKCU\...\CurrentVersion\Run`, value `InputWeave`), sending files and Send To (`%APPDATA%\Microsoft\Windows\SendTo\InputWeave.lnk`), notifications (`Notifier`, Windows App SDK App Notifications), small dialogs, File Explorer and the elevated service commands, the few Win32 calls WinUI has no API for, and the two COM objects it uses through their vtables (`ComCalls`: the Network List Manager and the Shell's shortcut).
  - `Strings/en-US`, `Strings/zh-TW`: the strings (`.resw`). English is the source; zh-TW uses Taiwan's terms.
  - `Assets/Tray/`: the tray icons, drawn by `scripts/MakeTrayIcons`. `Assets/AppIcon.ico` and `AppIcon.png`: the window's icon (16, 24, 32, 48, 64 and 256 px, each a PNG) and the title bar's at 32 px. `AppIcon256.png`: the same at 256 px, for the welcome page of setup and for notifications. All three are written by `apps/macos/scripts/make-brand-assets.swift`, with the macOS icon set.
  - `Assets/InputWeave.ico`: the app's icon (the executable, the Start menu shortcut, Settings › Apps), made by `scripts/MakeAppIcon`.
- `InputWeave.Core/`: everything that needs no UI, kept free of WinUI and Windows-only APIs. `Agent/` is the IPC client: the framing (big-endian u32 length, then the protobuf message, 4 MiB at most), the Hello, requests matched to responses by id, the service's events, every command the app sends, and reconnecting. `Canvas/` is the arrangement's geometry (as the macOS app's `CanvasGeometry.swift`) and the checks on desktop pictures. `Drag/` places the drag strips (`DragStrips`, the service's crossing rule, in pixels monitor by monitor), describes promised files (`FileDescriptors`) and decides a drag offered here (`DragStaging`: the staging folder, when the batch has arrived, drop or cancel, what follows the drop). `Overlay/` decides what the HUD says (`DragHud` for drags), how the cursor locator's copy grows and shrinks and where it goes to keep its hotspot on the cursor (`LocatorGeometry`), how a cursor's mask and color become premultiplied BGRA (`CursorPixels`) and which screen each monitor is when the screens are identified (`ScreenIdentity`); `Notifications/` decides when files and a stopped service get a notification, and which registry keys `--unregister` removes to take back the notification registration (the Windows App SDK's own `UnregisterAll` left all three in the installed build); `Setup/` holds the setup steps. `Panel/`, `Tray/`, `Settings/` and `Pairing/` decide what the app shows, by the macOS app's rules, as resource keys and values the app looks up; `Settings/ShortcutText` spells hotkeys out (Ctrl + Alt + Shift + L, or Ctrl+Alt+Shift+2 beside a name) from the service's `Status.hotkeys` and decides what a key pressed while recording does, and `Settings/Wake` what is offered for waking another computer from the service's `DeviceStatus.can_wake` and `wake`. The C# for `proto/inputweave/app/v1/app.proto` is generated at build time by Grpc.Tools; nothing generated is committed.
- `InputWeave.Tests/`: xUnit tests for `InputWeave.Core`, including the IPC client against a stand-in for the service, and a check that both languages have every string the code uses.
- `scripts/MakeTrayIcons/`: draws the tray icons (see below).
- `scripts/MakeAppIcon/`: makes the app's icon (see below).
- `scripts/package.ps1`: builds the MSI (see below).

The app writes its log to `%LOCALAPPDATA%\InputWeave\app.log`: the connection to the background service, its version, the state the panel shows, and the commands the service refused.

## Build

On Windows, with the .NET 9 SDK. NuGet restores everything else, the Windows App SDK included.

```bat
dotnet build apps\windows\InputWeave.sln -c Release
dotnet test apps\windows\InputWeave.sln -c Release
dotnet build apps\windows\InputWeave.sln -c Release -p:Platform=ARM64
```

The app ends up in `apps\windows\InputWeave\bin\x64\Release\net9.0-windows10.0.19041.0\win-x64\InputWeave.exe`. Run it as the logged-on user in that user's session: the agent's pipe lets in only SYSTEM and that user.

The version is the Cargo workspace version, read from `Cargo.toml` by `Directory.Build.props` at build time: the app, the background service and the MSI always carry the same one.

Of the Windows App SDK, only the parts the app uses are copied next to it: WinUI, Foundation, InteractiveExperiences and DWrite. The project still references the `Microsoft.WindowsAppSDK` metapackage (H.NotifyIcon asks for it) but excludes the assets of its `Runtime`, `ML`, `AI` and `Widgets` component packages; without `Runtime`, the self-contained files come from each component package instead of the whole runtime MSIX, so ONNX Runtime and DirectML (about 40 MB) stay out. Those references carry the versions the metapackage pins: update them together.

One file of the runtime is in no component package: `Microsoft.WindowsAppRuntime.Insights.Resource.dll`, which `AppNotificationManager.Register` loads from the app's folder (without it, registering fails with "The specified module could not be found" and nothing is notified). The Windows App SDK has no setting that brings it alone, so the `AddWindowsAppRuntimeInsights` target in `InputWeave.csproj` takes it out of the runtime MSIX that the `Microsoft.WindowsAppSDK.Runtime` package keeps in the NuGet cache (`tools\MSIX\win10-<x64|arm64>\Microsoft.WindowsAppRuntime.1.8.msix`, found through `GeneratePathProperty`), extracts only that entry into `obj\`, and copies it next to the app in the build output and the published folder, as the SDK does with its own files. The build fails if the MSIX or the file in it is missing, so an app that cannot notify is never published.

`dotnet publish` also trims (`PublishTrimmed`, `TrimMode=partial`): the .NET libraries and the Windows SDK and WinUI projections are cut down to what the app uses; the app's own assemblies and its other packages are kept whole. The trimmer reports two warnings (IL2104) about generic fallbacks inside CsWinRT (`WinRT.Runtime`, `Microsoft.Windows.SDK.NET`); they stay warnings. With trimming on, `dotnet build` also runs the trim analyzer, so code that trimming could break shows up as a warning, which `TreatWarningsAsErrors` makes an error. After a change to the app, run the published app, not only the built one:

```bat
dotnet publish apps\windows\InputWeave\InputWeave.csproj -c Release -r win-x64 --self-contained -o target\app\win-x64
```

The published folder is about 81 MB, 325 files (the untrimmed build with every Windows App SDK component was 216 MB).

## Installer

`packaging/windows/InputWeave.wxs` (WiX 5) installs the background service in `C:\Program Files\InputWeave` and the app in `C:\Program Files\InputWeave\App`, with a Start menu shortcut, InputWeave. `scripts/package.ps1` builds it the way CI does: `cargo build --release` of the service, `dotnet publish` of the app into a fresh `target\app\win-<arch>`, then `wix build` with `-bindpath App=<that folder>` (absolute: WiX looks for the files to harvest relative to the `.wxs`) and warnings as errors. From the repository root, with the Rust target, the .NET 9 SDK, and WiX 5.0.2 with `WixToolset.Firewall.wixext` and `WixToolset.Util.wixext`:

```bat
powershell -ExecutionPolicy Bypass -File apps\windows\scripts\package.ps1
powershell -ExecutionPolicy Bypass -File apps\windows\scripts\package.ps1 -Arch arm64
```

It writes `dist\InputWeave-<version>-<arch>.msi`, about 30 MB. What the MSI does for the app:

- Installs the published folder as it is: only `InputWeave.exe` is named in the `.wxs` (for the shortcut and the launch); the other files are harvested with `Files`.
- Before replacing or removing the app's files (installing, upgrading, repairing, uninstalling), ends every running `InputWeave.exe` in every session (`util:CloseApplication` with `TerminateProcess`). The service, the agent and the broker are `inputweave.exe` too, and Windows does not tell the names apart, so this runs after `StopServices` and only when the service's files change as well; running the installed package again, which changes nothing, ends nothing.
- Leaves Restart Manager on. With it off (`MSIRESTARTMANAGERCONTROL=Disable`), Windows Installer falls back to finding files in use by name: it took Explorer, the Phone Link and Intel graphics processes for users of the app's Windows App SDK DLLs, spent about 10 seconds per process on it, and with its normal UI asked to close them (Retry, Ignore, Cancel). With Restart Manager on, an upgrade with the app running took 16–17 seconds, with or without the UI, and asked nothing.
- At the end of an install, upgrade or repair, opens the app, not elevated (`WixUnelevatedShellExec`): the signed-in user's Explorer starts it, also when the installer runs from another session or as SYSTEM. If that fails, as it should when no one is signed in (not tried yet), the custom action ignores it and the install still succeeds.
- Does not make the app start at login itself. The app does that per user with the value `InputWeave` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, which it writes and removes itself (General settings).
- Uninstalling, but not upgrading, runs `InputWeave.exe --unregister` as the user who uninstalls (`WixQuietExec`, deferred and impersonated, after the running app has been ended and before its files are removed), which takes back what the app put in place for that user: the notification registration, the Send To shortcut, the Run value and the app's settings. Other users' items stay, pointing at a file that is gone.

## Tray icons

`InputWeave/Assets/Tray/<state>-<light|dark>.ico` are drawn from the geometry of the macOS menu bar icon (`apps/macos/InputWeave/Panel/StatusIcon.swift`): two screens and the two stitches between them, one bold change per state. Windows does not tint tray icons, so each state comes twice: `light` is the dark glyph for a light taskbar, `dark` the light glyph for a dark one; the app follows the taskbar's theme. Each file holds 16 to 64 px, each size drawn at that size. After changing the geometry, from the repository root:

```bat
dotnet run --project apps\windows\scripts\MakeTrayIcons
```

## App icon

`InputWeave/Assets/InputWeave.ico` is made from the macOS app icon, which `apps/macos/scripts/make-brand-assets.swift` draws from the brand geometry at each size with the detail that size keeps (`docs/brand/README.md`). It holds 16, 20, 24, 32, 40, 48, 64, 96, 128 and 256 px, each scaled down (WIC, Fant) from the smallest macOS drawing at least as large: 32-bit bitmaps, and PNG at 256 px. After the brand assets change, on Windows, from the repository root:

```bat
dotnet run --project apps\windows\scripts\MakeAppIcon
```

The window's icons, `Assets/AppIcon.ico`, `AppIcon.png` and `AppIcon256.png`, need no step here: the same script that draws the macOS icon set writes them.
