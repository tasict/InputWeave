# InputWeave for Linux: the app

The app is GTK4 and libadwaita, in Rust (gtk4-rs, libadwaita-rs). Like the macOS and Windows apps, it only talks to the background service (the agent) over its IPC and decides nothing itself (`docs/architecture.md` §2).

It is its own cargo workspace, not a member of the root one, so the root workspace still builds where GTK is not installed, such as on macOS and Windows. It shares two crates with the root workspace: `iw-proto`, for the IPC messages and their framing, and `iw-keymap`, for key names. It links nothing of the agent's.

- `core` (`inputweave-app-core`, no GTK): the IPC client (`agent.rs`), the app's view of the agent (`snapshot.rs`), every text decision (`status_text`, `transfer_text`, `device_text`, `pairing_text`, `clipboard_text`, `trouble_text`, `shortcut`, `size`), the edge glow's geometry, timing and pixels (`edge_glow`), when to notify (`news`, `service::ServiceWatch`), when to restart an outdated service (`service::is_outdated`), opening at login (`autostart`), the tray icon's shapes (`tray_icon`), the string catalogs (`strings/en.txt`, `strings/zh-TW.txt`, keys in `text/keys.rs`), and sample data for screenshots. It builds and tests on the Mac too.
- `app` (`inputweave-app`): the GTK part. `ui.rs` holds the app while it runs: the agent, the tray icon, the windows, and what follows when the agent's state changes.

## Building and testing

In the Linux containers (`scripts/linux-container/README.md`), with a target directory of its own so it does not wait on the root workspace's:

```sh
scripts/linux-container.sh run 'cd apps/linux && CARGO_TARGET_DIR=/target/app cargo test'
scripts/linux-container.sh run 'cd apps/linux && CARGO_TARGET_DIR=/target/app cargo clippy --all-targets -- -D warnings'
scripts/linux-container.sh run-arm64 'cd apps/linux && CARGO_TARGET_DIR=/target/app cargo build --release --target aarch64-unknown-linux-gnu'
```

The core alone, on the Mac:

```sh
cd apps/linux && CARGO_TARGET_DIR=<a local folder> cargo test -p inputweave-app-core
```

Against the real agent, with its mock backends (the agent built from the root workspace):

```sh
scripts/linux-container.sh run 'CARGO_TARGET_DIR=/target/app-agent cargo build -p inputweave && cd apps/linux && CARGO_TARGET_DIR=/target/app INPUTWEAVE_AGENT=/target/app-agent/debug/inputweave cargo test -p inputweave-app-core --test real_agent -- --ignored'
```

The GTK side on a display (Xvfb): entry rows left alone while edited, the inspector updated in place, switches following the model again after a failed command, the cursor speed sent as the pointer lets go of the slider (a real drag with xdotool) or once the keys stop, the wheel over it scrolling the page and leaving the speed, and going back when refused, pairing codes typed, pasted and cleared when wrong with the focus back in the first box, a new pairing attempt not showing the last one's outcome, the code window shown only while connected and coming back once closed, computers on the canvas snapping beside each other, springing back from an overlap, nudged with the arrow keys and moved back with Ctrl+Z (the SetArrangement commands sent, through `Agent::record_fixed`), and shortcuts recorded from key presses (the SetHotkeys sent) with a refusal said:

```sh
scripts/linux-container.sh run 'cd apps/linux && Xvfb :75 -nolisten tcp & sleep 1; DISPLAY=:75 GDK_BACKEND=x11 GSK_RENDERER=cairo GTK_A11Y=none CARGO_TARGET_DIR=/target/app dbus-run-session -- cargo test -p inputweave-app -- --ignored --test-threads=1'
```

The tray icon over D-Bus, against the mock agent: the item's icon, pixmaps and tooltip, the menu, and that clicking Pause Sharing pauses sharing in the agent and changes the menu and the icon:

```sh
scripts/linux-container.sh run 'sh apps/linux/scripts/check-tray.sh /target/app-agent/debug/inputweave /target/app/debug/inputweave-app'
```

Screenshots of every page (the arrangement with made-up desktop pictures), the troubleshooting page and the arrangement on GNOME's Wayland (`core::sample::wayland`: the permissions, the firewall hint, the session and the journal commands, and the line saying why there are no jumps), the shortcuts while recording and after a refusal, the HUD, a screen's name, the edge glow (blended, and the solid line beside it, over a made-up desktop), each setup step (with the permissions), the Add Device dialog and the pairing-code window, from sample data, in English and Traditional Chinese, light and dark (Xvfb, the cairo renderer), and a sheet of the tray icon in every state (`<language>-tray-icons.png`: the SVGs as the system's SVG loader draws them, and the pixmaps):

```sh
scripts/linux-container.sh run 'apps/linux/scripts/make-screenshots.sh /target/app-screenshots'
```

## How it works

- **One app per session.** The GApplication id is `cc.ctsite.inputweave`. A launch, first or again (a second one hands its command line to the running one), decides once: plain, it opens first-run setup until that is finished (Done or Later) and the main window after; with `--setup`, setup whether finished or not; with `--background` (login, or the agent opening the app), nothing, though a first one with no panel to show the tray icon opens the main window after 5 s. Over D-Bus, `Activate` shows the main window and the `background` action (`ActivateAction("background")`) only makes sure the app runs, which is what the agent can call to have it hold a question for the user. `--version` prints and exits before GTK starts. For testing: `--page <general|devices|arrangement|files|troubleshooting|license>`, `--socket <path>`, `--language <en|zh-TW>`, `--screenshot <folder>`, `--setup` (first-run setup, finished or not), `--show-hud <text>`, `--show-identify` (the screens' names for 20 s), `--show-locator`, `--show-glow <left|right|top|bottom>` (that edge of the first monitor lit, as if the cursor crossed it a third of the way along).
- **IPC.** `$XDG_RUNTIME_DIR/inputweave/agent.sock`, as the agent's `paths.rs` puts it. A thread per connection reads the socket and applies what the agent sends to the snapshot in order, a command's answer before any event after it. Commands are futures the GTK main loop awaits; they go out through a writing thread, so nothing waits on the socket, and a write that fails or that the agent does not take in 10 s ends the connection, which starts over, rather than leave half a frame on it. Deadlines are checked as the thread goes, not only when the socket is quiet. Each message is one change to the snapshot, which the UI shares (`Arc`); the arrangement (with its previews) and the transfers are behind their own `Arc`, so changing the snapshot while the UI holds it copies little. Reconnects from 250 ms, doubling to 2 s; a command unanswered in 10 s fails.
- **Tray icon.** A StatusNotifierItem with a `com.canonical.dbusmenu` menu, written with zbus (not ksni, whose Unlicense is not on the allow list). KDE Plasma shows it natively, GNOME through the AppIndicator extension, which Ubuntu turns on. Without a `org.kde.StatusNotifierWatcher` on the bus 5 seconds after a `--background` start (at login the panel may come up after the app), the app opens its window rather than run with nothing to find it by; it registers whenever a watcher appears later. The icon is the macOS one's geometry (`StatusIcon.swift`): symbolic SVGs written to `$XDG_RUNTIME_DIR/inputweave/app/icons` and named through `IconThemePath`, so the panel tints them like its other icons; they use fills and clip paths only, as symbolic icons are tinted by setting fills. Pixmaps drawn with cairo (white) go along for panels that ignore the name.
- **Pairing.** The code window shows only while the agent is connected (the client drops the pairing state when the connection ends); closing it declines the code, and it shows again only for another code. Add Device shows Connecting from Start until the agent has answered StartPairing, as until then its pairing state is still the last attempt's; StartPairing has no deadline of the app's (the agent answers as soon as it has resolved the address), and closing Add Device cancels only a pairing this dialog started: one still starting is cancelled when the agent takes it, nothing if it refuses. A code that could not reach the agent stays, and Enter sends it again; a wrong code (asked for again with fewer tries left) clears the boxes and gives the first the focus. Commands the agent takes long over have their own timeouts (`agent::timeout_for`: a pairing code 35 s, past the agent's 30 s; sending files 120 s).
- **Restarting the service** counts as done once systemd runs the unit as another invocation (`InvocationID`), even if no poll saw it stop; until then its stopping is no news.
- **Keeping up with the model.** The tray, notifications and pairing follow every change and the 1 s tick; the main window only while it is shown, and then only the page shown (a page is brought up to date when chosen, the window when presented). Pages build their widgets once and update them from every model; controls the app sets itself do not send commands back (`pages::Quiet`), so a switch whose command failed shows the model again on the refresh that follows. Entry rows are left alone while the user edits them (`pages::EntrySync`: focus within the row, or a change not applied yet; the row itself never has the focus). The inspector's rows are made again only for another device or other screens.
- **Strings.** `core/strings/*.txt`, one `Key = value` per line, taken from the Windows app's `.resw` with Linux words where they differ (Show in Folder, the Super key). The language is `LANGUAGE`/`LC_ALL`/`LC_MESSAGES`/`LANG`, Traditional Chinese for any Chinese but Simplified. Tests check both catalogs have the same keys and placeholders, and every key the code uses.
- **Sizes** follow GNOME (GLib's `g_format_size`): 1000 bytes to the kB, one decimal. Each app follows its own platform.
- **The background service** is the user's systemd unit `app-cc.ctsite.inputweave@agent.service` (`core::service::AGENT_UNIT`, the package's template unit; xdg-desktop-portal tells the app id from the name), read every 2 s and started or restarted through the user manager's D-Bus API. Before StartUnit or RestartUnit the app gives the user manager this session's `DISPLAY`, `WAYLAND_DISPLAY`, `XAUTHORITY`, `XDG_SESSION_TYPE`, `XDG_CURRENT_DESKTOP` and `XDG_SESSION_ID` (SetEnvironment), as the package's `start-agent` does at login: the manager outlives a session. Not from an app systemd runs as a service (`core::service::under_systemd`: the leaf of `/proc/self/cgroup` is a `.service`, as with D-Bus activation or an autostart entry made a unit; `INVOCATION_ID` alone is no evidence, as whatever a service starts inherits it), whose variables are the manager's: that relies on the session having given them at login (graphical-session.target, or `start-agent`). Only from the local graphical session (`core::service::session_import`: `XDG_SESSION_TYPE` x11 with a local `DISPLAY`, or wayland with `WAYLAND_DISPLAY`, and no `SSH_CONNECTION`/`SSH_CLIENT`/`SSH_TTY`), so an `ssh -X` shell or a partial launch passes on nothing; and a variable the app lacks is taken away (UnsetEnvironment) only when the manager has it from this same session (its `XDG_SESSION_ID` is the app's, or it has none), read from the manager's `Environment`. The app never enables it: the package enables it for every user, and a user who turned it off for themselves keeps it off; Start runs it for this session.
- **An outdated service** is restarted once per launch, as the macOS app does (`core::service::is_outdated`, `OutdatedWatch`): when it refuses the app's IPC version with an older one of its own (its refusal says "agent speaks IPC version N", `agent::ipc_version_in`; a newer one means the app is the old one: logged, and the window and the tray say "This app is older than the background service" with "Quit InputWeave and open it again", and the agent is left running; one that does not say is left alone), or is another build than the agent packaged beside the app (at most once per packaged agent: the digest it was restarted for is kept in `app.toml`, so a restart that changed nothing is not repeated at every launch; the same build never counts as outdated, whatever the versions say; only an agent too old to report its digest is judged by its version, which is why `packaging/linux/build-deb.sh` fails when `apps/linux`'s version is not the root workspace's, as core's `the_version_is_the_root_workspaces` test does) (the SHA-256 of `inputweave` next to the app's executable, read on a thread of its own at start and again when its time or size changed, which is looked at every 30 s and when the unit's state changes, against `AgentHello.agent_digest`), and only while the unit runs it. apt replaces the files but restarts no user service, so an app left running across an upgrade restarts the agent too.
- **Logs** are in the systemd journal; there is no log folder. Troubleshooting shows two commands with a copy button: the agent's unit (`journalctl --user -u app-cc.ctsite.inputweave@agent.service`) and the app's identifier (`journalctl --user -t inputweave-app`: systemd's default `SyslogIdentifier` is the executable's name, the same whether the app runs as its own unit for D-Bus activation or as the unit `systemd-xdg-autostart-generator` makes of its autostart entry; from a terminal it writes there). Diagnostics hold only the agent's journal: the app's may name files.
- **Troubleshooting** also shows, from the agent's status: the permissions the desktop's portals ask for (remote control and input capture, on Wayland) with Allow… (RequestPermission; the desktop shows its own dialog), what came of the last time (being asked, restoring what was allowed before, not allowed, failed and why, stopped from the desktop: Allow Again…), and that GNOME asks for input capture at every login; that the clipboard on GNOME waits for remote control (the CLIPBOARD backend is the agent's "Clipboard portal", `trouble_text::CLIPBOARD_PORTAL`, with a problem); none of it while the agent cannot be reached; a firewall hint when ufw blocks the agent's port or mDNS, or is on and unreadable, with `sudo ufw allow InputWeave` (and the port, when not 47820) to copy; and the desktop session (X11 or Wayland, the desktop) with what serves each part (the agent's technical names and its problems in English, as in its diagnostics). All of it in `core::trouble_text`; the ports and the ufw command are the agent's and `inputweave ctl`'s (`iw_proto::network`). Rows showing names, the agent's words or commands have Pango markup off (`pages::plain_row`, set before their text), so `&` and `<` show as they are.
- **Jumps on Wayland.** Where the agent says the cursor leaves only across edges (`Status.cursor_leaves_at_edges_only`), no jumps to other computers are offered: Move Cursor Here is off, their jump shortcuts are not shown beside the names (this computer's is, as jumping back here works), and the arrangement and the jump shortcut's row say why; a jump refused with `edge_only` says it too. Computers that paused sharing or cannot take input are left out of jumps as well, with their connection text saying so.
- **Open at login** is an XDG autostart entry, `~/.config/autostart/cc.ctsite.inputweave.desktop`, that runs the app with `--background`; an entry the desktop turned off (`Hidden=true`, `X-GNOME-Autostart-enabled=false`) counts as off.
- **Notifications** go through GNotification: files received (Open Folder), files waiting for an answer (Accept, Decline), the service stopped (Start Service). Their buttons are app actions, so they work while only the tray icon is up. A command from the tray menu or a notification that fails says so in a notification of its own (withdrawn after 10 s), as there is no window to show it in; with the window shown, in the window.
- **Drags across computers.** Linux takes no part (GNOME offers no way to put drop strips at the screen edge): the app never sends `BeginDrag`, and the Linux agent declines every `DragOffer` itself and offers its app no drag carried back. A `DragArrived` that comes all the same (another backend, an older agent) is declined at once, so the other computer is not left waiting. Files go with Send Files…, dropping on the arrangement, or copy and paste.
- **The arrangement** (`canvas.rs`) is a `GtkDrawingArea` drawn with cairo and pango: the geometry is `core::canvas`, ported from the other two apps' `CanvasGeometry` with all their test cases (fit, union, seams and stitches, snapping 8 view units, overlap, the label's tile, the name beside the jump shortcut, the badge's frame, hit testing). Desktop pictures (`Screen.preview_jpeg`) are checked first (`core::desktop_picture`: a JPEG of at most 512 KB whose frame header says 1–4096 pixels a side), decoded by GDK and kept per computer and screen until their bytes change; high contrast shows none. Dragging a computer snaps it, an overlapping drop springs back and shakes, arrow keys move the selected one by 10 view units, Ctrl+Z undoes a move; every move is one SetArrangement. The right-click menu moves the cursor there (JumpTo) or renames another computer, which puts the cursor in the inspector's name. Files dropped on a computer that takes them are sent to it. "Synced to N devices" shows for 2 s after the arrangement changed with others connected.
- **First-run setup** (`setup.rs`): welcome, name, permissions (only while the agent reports a portal permission, remote control or input capture, that is not granted and neither being asked nor restored: a row for each with Allow…; passed over, going on or back, once nothing there is left to do, `core::setup::go`), connect (the Add Device dialog over the setup window, so connecting and the code are one step), arrange (a canvas of its own) and try it (`core::setup::worked`: the cursor on another computer, or a return since the step opened). The permissions step joins whenever there is something to do there and the user has not gone past it (the agent may answer only after the window opened), and stays once shown; "Step n of N" and the bar count the steps gone through (`core::setup::shown`). It opens on a plain launch until Done or Later (`app.toml` beside the agent's configuration, `core::settings`), and from the tray menu's Run Setup Again….
- **Shortcuts** (`pages/shortcuts.rs`): four rows (the relative mouse only when the service has it), each with Record, the jumps and the relative mouse with a switch, and Reset Shortcuts (off at the defaults, `core::shortcut::is_default`). Recording listens in a focused box: GTK's hardware keycode is the evdev code plus 8 on X11 and Wayland, named through `iw-keymap` (`core::shortcut::key_name`); Esc alone cancels, Delete or Backspace alone goes back to the default, a modifier alone waits, the jumps take the modifiers. The whole set goes in one SetHotkeys; a refusal says why under the rows, naming the shortcut a duplicate clashes with by the service's own rule (`core::shortcut::clash`). Combinations the agent holds back (the lock and the jumps, on X11) never reach the app, so they cannot be recorded, as on macOS.
- **The edge glow**: every `Event.cursor_crossed` is an event of its own (the IPC client queues them, `Agent::take_crossings`, so a crossing out and straight back is two, and calls a callback of their own, `Agent::on_crossing`, so the glow is lit at once rather than with the next full refresh; crossings queued before the callback is registered are dropped), lighting the crossed edge of the monitor the agent names (`core::edge_glow`: the macOS and Windows apps' geometry with their test cases; brightest where it crossed, at least 35 % at the ends, about 24 px deep at the monitor's scale; 0.1 s in, 0.3 s held, 0.4 s out; each (monitor, edge) on its own clock, crossing it again while it shows carries on from its opacity and slides the brightest part from where it is now, `Glows`). With animations off (`gtk-enable-animations`) it shows at once for 0.5 s and jumps; with high contrast it is a solid 4 px line. On X11 it is an override-redirect window with an empty input shape: with a compositor (a `_NET_WM_CM_S<n>` owner) of a 32-bit visual drawn anew every 16 ms while it fades or slides; without, the solid line, filled by the server. With the layer shell, a layer surface on the output the agent names: by its name (wl_output 4), else by its place and size (xdg-output, as `edge_glow::monitor_for` finds X11's monitors; an output without a name is `output-<global>` to the agent), anchored along the edge, over panels (exclusive zone -1), drawn into two buffers of one shared-memory pool in turn (never one the compositor has not released); after the output's size changes the old pool stays until a buffer of the new size is committed, and a glow that cannot be drawn is left out (said once) while the others go on. On X11 whether a compositor runs is followed through XFixes' selection events (asked at most every 5 s without XFixes), not asked at each crossing. Frames that would look as the last one (held, or the spot at rest; `edge_glow::unchanged`) are not drawn, and the overlay thread sleeps until a glow's next phase (`Glows::wake`: frames only while one fades or slides, each due a frame after the last one drawn, then until its hold ends; a solid line until it is gone). General shows whether it can show without making the overlays to ask (`Ui::glow_availability`; before they are made, GNOME's Wayland from the agent's session, `edge_glow::expected`). On X11 the thread reads the server's events before each frame and at least every 50 ms while a glow shows, so an exposed glow is drawn whole again at once. A crossing of an edge whose surface the compositor closed, or that is now on another output, makes the surface anew. GNOME's Wayland shows none, and no notification stands in. The switch is in General › Switching (`edge_glow` in `app.toml`, on by default), off with a line saying why where nothing can show it: GNOME's sentence for a Wayland without the layer shell on GNOME (the desktop as the agent reports it, the app's own `XDG_CURRENT_DESKTOP` only without), a neutral one when the overlays could not start or lost the display server (`edge_glow::hint_key`).
- **The HUD, identifying screens and finding the cursor** (`overlay/`): what the HUD says is `core::hud::HudWatch` (the Windows app's `HudWatch` with its tests; the take-back hint's count lives in `app.toml`). Where it shows depends on the session: on X11 in override-redirect windows of the app's own over x11rb, cut to their picture with the SHAPE extension (no compositor needed) and with an empty input shape; on Wayland with the layer shell (KDE Plasma, wlroots) in a layer surface of a Wayland client of the app's own (gtk4-layer-shell is not in Ubuntu 24.04); on GNOME on Wayland as a notification. One overlay thread owns the X11 connection (or the Wayland one): it draws at the scale of the monitor or output the overlay goes on, repaints on Expose, takes things down when their time is up (also while the cursor is being shown), keeps one graphics context, asks X's primary output once (again after RandR says the outputs changed), and on Wayland reads the compositor's events all along (it waits on the compositor's socket and an eventfd the app writes with each note, waking for nothing else), so outputs plugged in later and their scales are known, and destroys every surface it made; windows that fail part way are taken down at once, and windows showing a picture have no background, so nothing black shows before it is drawn. When the thread loses the X server or the compositor, the HUD falls back to notifications (and identify, on X11, to the fullscreen windows). Identifying screens on X11 is drawn the same way: a frame of four plain windows and the name's card on each monitor, so it needs no compositor and takes no focus; on Wayland it is a fullscreen window on each monitor, transparent and with an empty input region, which may take the focus for its 2.5 s, and some compositors may not honour the empty input region. The cursor grows (4 times, then back over 1.1 s) only on X11, from XFixes' cursor image; Wayland does not tell an app where the cursor is, and GNOME has its own Locate Pointer.
- **Relative mouse when a game holds the pointer**: refused, the switch's hint says so in red until the service reports another value or cannot be reached, as on Windows.
- **The license** (docs/architecture.md §11): a License row pinned at the sidebar's foot ("Trial", or the woven "Licensed" label), the License page it opens, and About (a dialog of its own in AdwAboutDialog's shape, from the sidebar's menu and the tray menu, so "Trial" with Buy a License…, or the label, shows at once rather than under Details); nothing else in the app mentions it. The agent keeps the record; `core::license::Keeper` keeps one outbox of requests, sent oldest first, one at a time to Polar and one at a time to the agent (a slow Polar never holds up the agent), each waiting on its own after a failure (1 minute doubling to 30, or Polar's `Retry-After`) and each safe to send again: activate a key waiting for it (labelled with this computer's name); after a 403, a validate without activation to tell seats full from invalid; validate a licensed computer at most every 30 days, only while the License page or About is open, invalid only after two 404s a minute apart, nothing changing while Polar can't be reached; each answer reported to the agent as a `RecordLicenseResult`; activations freed with Polar (also while the agent is not running); RemoveLicense. A grant from Polar is on disk before it is reported, so a key is never activated twice, and one the agent holds already is done. Any error code the agent answers a grant with, known or not, frees the activation and stops that key, said in the dialog, until the user enters it again or the agent's record changes; only `license_unavailable` and `agent_stopping`, and no answer at all, are tried again. A grant is reported only once it is on disk. Entering a key drops what its last try came to and clears every wait ahead of it, except a minute after a failed activate (it may have granted a seat all the same) and a wait Polar asked for with a 429. The dialog follows the record only from the agent's answer to the key, so an earlier try's seats full or invalid never shows for this one; while Polar can't be reached it says so and keeps following. What must outlive the app (grants not reported yet, activations to free, a Remove License on its way) is kept in `$XDG_CONFIG_HOME/inputweave/app-license.json` (0600). A file it can't read is left alone and read again each minute, with no license work meanwhile; one that isn't an outbox is moved to `app-license.json.bad`. After three failed writes in a row, or while the file can't be read, the dialog says the license couldn't be saved; it also says when the background service hasn't answered for 10 s. A 200 from activate without a readable id is never asked again by itself. What the pages show about this work is read off the outbox and the agent's record. `core::polar` builds the requests and reads Polar's answers (tested against `testdata/polar`); the app sends them with ureq over rustls (ring, passed to ureq explicitly, and the system's CA store read by rustls-native-certs; no bundled roots) on a thread of their own, `User-Agent: InputWeave/<version>`, 20 s timeout (60 s for activate, labelled with this computer's name tidied to at most 64 characters); a 422 means an invalid key only when Polar says it is about the key; `INPUTWEAVE_POLAR_URL` points it at `scripts/mock-polar.py`. Enter License Key is an `AdwDialog` that stays open while the key is activated and closes once it is, the label sewing its stitches around once (`woven.rs`; at once with animations off, a solid stitch with high contrast). Remove License asks first, then sends RemoveLicense and, once the agent took it, frees this computer's seat with Polar: a spinner while the first try runs, a note once it failed (it keeps trying; a refusal for good drops it and says so once), and while the seat still waits for Polar a note with Manage Computers… (the customer portal), also after a restart. A key the agent refused stays left alone across restarts.
- **Updates** come through the system's package manager from the package source the `.deb` installs (docs/architecture.md §12.4); General › Updates shows the version and the source, and the app checks nothing itself.
- **Brand.** Only the five brand color tokens, as `@iw_thread` and so on, swapped for the dark set as the style manager turns dark; everything else is libadwaita's.
